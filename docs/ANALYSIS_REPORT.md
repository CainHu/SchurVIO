# 视觉后验作用与噪声敏感度分析

配套的交互式图表报告：**`out/report.html`**（自包含单文件，双击用浏览器打开，无需联网或任何依赖）。

## 如何生成

```bash
cmake --build cmake-build-release --target VinsAnalysis VinsReport

# 基线(默认 uv_var=400, 过程噪声 scale=1.0)
./cmake-build-release/VinsAnalysis.exe 400 base 1.0

# 噪声扫描
for v in 200 400 800 1600 3200 6400; do
  ./cmake-build-release/VinsAnalysis.exe $v "uv$v" 1.0
done
for s in 0.5 0.6 0.8 1.0 1.2 1.5 1.8 2.0 2.5; do
  ./cmake-build-release/VinsAnalysis.exe 400 "proc$s" $s
done

# 生成 HTML
./cmake-build-release/VinsReport.exe      # -> out/report.html
```

报告包含 7 个部分：总体精度、3D 轨迹可视化（可旋转，含特征点与机体坐标系）、
视觉后验修正作用、误差/协方差一致性、零偏与重力收敛、噪声敏感度、观测量统计。

---

## 一、总体精度：融合本身是正常工作的

| 指标 | 数值 |
|---|---|
| 位置 RMSE | **0.106 m**（轨迹半径 5 m，100 s） |
| 速度 RMSE | 0.022 m/s（运动速度 1 m/s） |
| 姿态 RMSE | 0.040°（7.0e-4 rad） |
| 最大位置误差 | 0.214 m |
| 末帧位置误差 | 0.024 m |

100 秒、2001 帧下位置误差始终在 0.02~0.21 m，**没有漂移累积**，
姿态精度到 0.04°。轨迹图上 GT 与 EST 两条线基本重合。
**结论：视觉后验确实在起作用，融合结果是可用的。**

零偏与重力的估计也在收敛（报告第 5 节）——这几个量只能通过视觉更新间接可观，
它们收敛本身就是"视觉信息确实进入了滤波器"的独立证据。

## 二、但视觉后验的修正力度严重不足

这是分析中最值得注意的发现。

| 指标 | 数值 | 含义 |
|---|---|---|
| 视觉更新次数 | 1996 | |
| **位置改善率** | **50.5 %** | 后验比先验更接近真值的比例 |
| 平均修正量 `\|dx_p\|` | 8.7e-4 m | |
| 平均位置误差 | 0.0895 m | |
| **修正量 / 误差** | **0.97 %** | |

**改善率 50.5 % 等于抛硬币**，而修正量比误差小两个数量级。
报告第 3 节的散点图（先验误差 vs 后验误差）能直观看到：
点几乎全部贴在 y=x 对角线上，说明每次视觉更新对状态的改变微乎其微。

> 注意：这**不代表滤波器没用**。整体精度好，是因为 IMU 预积分本身很准，
> 加上视觉在长期上抑制了漂移（对比纯 IMU 会明显漂移）。
> 问题在于单次更新的增益太小，视觉的信息没有被充分利用。

### 根因：位置协方差被高估了 3 个数量级

报告第 4 节：

| 量 | 实际误差 | 滤波器认为的 σ | 比值 |
|---|---|---|---|
| 位置 | 0.024 m | **86.6 m** | 2.7e-4 |
| 姿态 | 5.5e-4 rad | 0.752 rad | 7.3e-4 |

`sigma_p` 从初始 0.17 m **单调增长到 86 m**，而真实误差始终在 0.1 m 量级。

**为什么会这样**：`predict` 每步都往协方差加过程噪声，
而视觉更新只能压缩 `Hpp` 值域内的方向——**gauge 零空间（全局平移 3 维 + 旋转 3 维 + 尺度 1 维）
永远收不回来**（见 [HPP_NULLSPACE.md](HPP_NULLSPACE.md)）。
所以位置协方差在全局方向上单调发散。

这在数学上是**正确的**——纯视觉确实无法确定全局位置。但后果是
`K = P·hᵀ/(h·P·hᵀ + R)` 中的 `P` 严重虚高，增益分配失衡。

## 三、协方差失去正定性（数值缺陷）

分析顺带暴露出一个明确的 bug：

```
WARNING: 142/2001 帧的协方差 trace 为负(失去正定性)
首次出现在 t = 92.9 s，速度分量 trace = -5.71
```

对称矩阵 trace 为负意味着**至少有一个负特征值**，协方差矩阵已不是有效的协方差。

这是序贯更新中 Joseph 形式累积舍入误差的典型症状。当前**未导致发散**
（因为增益本来就很小），但会让增益计算失真。

建议排查方向：
- 序贯更新循环中 `cov_p.triangularView<Upper>() += (K*R - PhT)*K^T` 的数值稳定性
- 考虑周期性做对称化 + 特征值截断（把负特征值钳到 0）
- 或改用平方根滤波（UD 分解），从根本上保证正定性

## 四、噪声参数敏感度：当前配置在悬崖边

### 量测噪声 `uv_var`

| uv_var | 位置 RMSE | 状态 |
|---|---|---|
| 100 | 33493 m | **发散** |
| 200 | 215 m | **发散** |
| **400** | **0.106 m** | 稳定（当前默认） |
| 800 | 0.146 m | 稳定 |
| 1600 | 0.203 m | 稳定 |
| 3200 | 0.284 m | 稳定 |
| 6400 | 0.397 m | 稳定 |

**当前默认值 400 正好压在发散边界上** —— 降到 200 就炸。
向上则精度单调线性变差（过度不信任视觉，逐渐退化成纯 IMU 递推）。

这与"协方差被高估"是同一个问题的两面：`P` 虚高，就必须把 `R` 也调大才能平衡；
一旦 `R` 调小，增益暴涨，滤波器立刻发散。

> **实用建议**：不要把 `uv_var` 往下调。若要提升精度，
> 应该先修协方差高估的问题，而不是调 `R`。

### 过程噪声缩放

| scale | 位置 RMSE | 状态 |
|---|---|---|
| 0.5 | 146 m | **发散** |
| 0.6 | 0.121 m | 稳定 |
| 0.8 | 0.112 m | 稳定 |
| 1.0 | 0.106 m | 稳定（当前默认） |
| 1.2 | 0.101 m | 稳定 |
| 1.5 | 0.094 m | 稳定 |
| **1.8** | **0.090 m** | 稳定（**最优**） |
| 2.0 | 1533 m | **发散** |
| 2.5 | 104 m | **发散** |

稳定区间只有 **[0.6, 1.8]**，两侧都是断崖式发散。

**最优值不在 1.0 而在 1.8**（RMSE 0.090 vs 0.106，改善 15 %），
说明当前过程噪声配置**偏小**。但 1.8 距离 2.0 的发散点太近，
实际使用建议取 1.2~1.5，兼顾精度与裕度。

## 五、结论与建议

**视觉后验是否正确修正了状态？** 是的，但**修正力度只有应有的百分之一**。
整体精度好主要归功于 IMU 预积分的质量，视觉的贡献没有被充分发挥。

按优先级的改进建议：

1. **修协方差高估**（收益最大）。位置协方差涨到 86 m 是不合理的。
   常见做法是对不可观方向做显式约束（如 FEJ、可观测性约束 OC-EKF），
   或对全局位置/偏航施加弱先验，阻止协方差在 gauge 方向上无限增长。

2. **修协方差正定性**（142 帧 trace 为负）。用平方根滤波或周期性特征值截断。

3. **过程噪声调到 1.2~1.5**（改善约 10 %，零成本，但注意 2.0 就发散）。

4. **不要动 `uv_var`**。它当前处在稳定边界，调小必然发散；
   调大只会更差。它的值实际上是在补偿问题 1，修好 1 之后才有调整空间。

前两条是同一个根因的两个表现，值得一起处理。
